## 推荐小步骤

0. 实施契约：确认框架、模型/Embedding、规模/语言、生命周期、关键测试接口。候选 FastAPI、React+TypeScript+Vite、托管模型；具体模型取决于凭据和部署条件。验收：能说清支持什么、何时可查询、重启发生什么。
1. API 和早期 Docker：配置、健康检查、依赖锁定与 Linux 镜像。推荐最终单容器交付静态前端与 API，开发分别运行；双容器更独立，但多出代理与配置。验收：镜像安装、启动、健康检查成功，不把它当作端到端通过。
2. 上传与生命周期：独立上传 ID、限额、明确失败，完成后才发布可查询数据。推荐同步处理先闭环；规模和模型等待不适合时选进程内后台处理+轮询，增加中断语义，不能宣称任务持久可靠。候选临时文件+内存状态、单进程，重启清空且明确告知；若需重启保留，再选 SQLite/卷并明确恢复。验收：同名不混同、半成品不可查、失败不 ready。
3. PDF 到证据：候选 pdfplumber 布局文本、页内分组再受限切块；保留型号、表头、单位、条件。纯文本切块更简单但易失关系，重型结构解析增加资源和验证成本。验收：通过解析 Interface 核对开发材料条款及 Rondel/Highbay 关系、物理页码；无文本不算正常空文档。用 pdf 技能核对真实样本；不宣称自动发现所有错误参数组。
4. 最薄前端：浏览器上传、状态、选择和证据预览。React+TypeScript+Vite 为候选；原生页面减少构建依赖但状态需手工维护。验收：新上传内容真实可见，失败可见，选中 ID 正确传递；实施新 UI 使用 frontend-design。
5. CSV 精确查询：候选标准库 csv+Decimal，按文档/订单号索引并保留重复记录。pandas 有利后续聚合，当前非必需。验收：完整文件、多订单号、前导零、金额分隔符、空值、原始列值与记录号；合成带引号换行样本验证逻辑记录号。聊天入口候选经校验的结构化查询计划；显式查询模式更确定但增加交互。不得用模糊结果代替精确未命中，不用保留记录调参。
6. PDF 检索：推荐 Dense 基线，小规模内存向量计算；BM25 可先作管线冒烟，如选为最终替代路线需确认。有证据再接 BM25+RRF，暂不默认增加向量数据库。验收：top_k 前文档范围过滤、稳定证据 ID、开发题所需证据入选。Embedding/切块版本变化需重建；fusion/lexical 正式测试随实际接入补齐。
7. 回答与引用：统一问题入口，内部 PDF 检索或 CSV 精确查询；模型依证据作答，引用 ID 回查。推荐完整 JSON 返回，暂不承诺多轮指代；SSE/逐 token 留后。验收：条款、参数、CSV 回答可核对；无效/越界引用不展示为有效，超时/无依据/精确未命中区分。有效引用不等于事实支持，仍人工核对。
8. 浏览器与 Docker 闭环：补聊天、来源、静态构建、运行配置、README、dockerignore；从空状态新上传 PDF/CSV 完成冒烟，不借开发索引或答案集。模型密钥仅后端运行时注入。两条路径冒烟不替代 M3 多文档/状态/失败矩阵。

- 候选流程：浏览器上传中；服务器 queued → processing → ready/failed，processing携带解析/建立索引阶段。单进程有界后台串行摄入，前端轮询；不引入外部任务队列。相较前轮同步建议，长册及模型限流使后台处理更有价值。
- 文档ready只表示有已完成、可查询的证据，不表示每页内容都被理解或该问题必可回答。无可用文本失败；已知跳过页/不支持内容显示范围警告，不能泛用警告掩盖已承诺参数关系错误。
- 用户必须显式选择ready文档；未就绪文档不可选，已选有效范围可在其他文件处理中继续问。每个请求冻结选择ID，后台校验；无选择/含非ready项不偷偷查询其他文档。改变选择不改写已发请求或历史回答的来源标签。
- 回答状态独立于文档：调用模型超时/限流不把已ready文件改成failed；短期限流有限重试，无法恢复时保留问题供重试，日额度耗尽不循环请求。
- 推荐因限流问题改选持久化：单机SQLite保存元数据/证据/向量，原文件放Docker命名卷；ready与证据提交保持一致。重启保留已完成资料，内存索引从持久数据恢复；中断任务标为failed并可手动重试，不宣称崩溃任务自动续跑。模型/切块版本不兼容时提示重建，不无声反复调用API。聊天首版可仅保留当前浏览器会话，需明确页面刷新后行为；不承诺持久对话历史。
- 关键验收建议：刷新不重复提交；重启不重新Embedding已完成且版本兼容的文件；中断任务有明确结果；CSV查不到不伪造近似值；新上传不能改变已经提交的问题范围。这些测试接口尚待统一确认。

单双容器取舍：
- 单容器：React构建产物由FastAPI静态提供，运行只有Uvicorn；Node只在构建阶段。一个端口/同源/一份部署产物，少代理配置；前端改动需重新构建交付镜像，API停则静态入口也停，静态吞吐与后端共同部署。适合当前本地小规模交付。

- SQLite在应用进程内，不需要第三个数据库容器；未来若SSR、静态流量或独立发布需求明确，再考虑拆分。
